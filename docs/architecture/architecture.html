VM Migration Factory

Turning two working single-VM conversion scripts into a fleet-scale migration tool a customer can run against hundreds of VMs — with assessment, wave planning, parallel orchestration, validation gates, rollback, and reporting — fully testable in a lab. It moves standalone machines from older sizes (the A v2, B v1, D, Dl, E and F families, v1 to v5, Generation 1 and 2) to current ones: D, Dl and E on v5, v6 and v7, and Bsv2 for a B v1 machine. Microsoft also lists F on v7, but every F v7 series is AMD and every F, Fs and Fsv2 machine is Intel, so the product offers no F size (F-V7-SCOPE-WORDS-1). A move to v6 or v7 also changes the disk controller from SCSI to NVMe.

Revision 2026-11-10 — SCHEDULE-PASS-DUE-1: the five-minute schedule pass reads only what is due

§4/§9/§11. The schedule pass read every run in the store - about 530 store calls and its whole 210-second budget, every pass - though almost no run had anything due, and it runs in the same service as the dashboard’s calls. It stays in that service (no new function app, no new job) and now reads only what is due. A record at the top of the store, schedule-due.json (schemas/schedule-due.schema.json), lists the runs the pass checks. Five paths add a run, each AFTER the write that makes the run due, through one module function (Add-VmfRunScheduleDue) called by the cmdlet that writes the fact - Set-VmfWaveSchedule, Approve-VmfPlan, Resolve-VmfDecision, Clear-VmfWaveHalt, Start-VmfWave, New-VmfPutBackJob - and by the service for its engine start, so a person at a console marks a run as the service does: an engine start of a wave, a restore or a finish (the run can stop part way, so a wave or a restore must start again, a hold must go, and the next wave of a signed-off plan must start; the run is held in the record 15 minutes, because Azure can list a new execution late and the engine writes its first hold only when its container runs); a schedule saved (its wave starts at its time); a plan sign-off (the next wave starts when one finishes); a decision or a retry of a machine (the machine goes back to a working state, and the pass starts its wave again when no part of it runs); and Resume (the pass starts again what the brake held). After it checks a run, the pass keeps it while one of its checks still acts on it (Get-VmfRunScheduleNeed: a machine at a working state, a restore or a finish on a machine record that the service did not give up on, a hold of a wave worker that is live, or old on a machine at a final state or with no record, a sign-off of a plan that has not run every wave, a schedule) or an engine execution of the run still runs; a run whose only fact is a scheduled wave waits in the record until its time (nextUtc). Otherwise it removes it. The removal is one version-checked write (Write-VmfStoreRootTextIfVersion, the If-Match of PLAN-WRITE-RACE-1, at the top of the container), and removes an entry only while it holds the mark id the pass read: a path that marks the run during the pass writes a new mark id, and its entry stays. The safety net: once an hour the pass checks every run, as each pass did before (the sweep), and adds any run it finds a fact for - a mark that could not be written waits at most an hour. A due record that is not there or cannot be used starts a sweep at once, and so does a pass that could not write what it found. The pass record (schedule-status.json, schema 2) keeps the budget and the place of an open sweep, and names the run each pass is on, so a pass the host stops is counted against that run; a due run with one stop is checked last of the due runs, and at two it is passed over once and added to the record for the next pass. Measured on a test store of 20 runs with one run due: 351 store calls for a pass that checks every run, 26 for the pass after it, 4 for a pass with nothing due.

Revision 2026-11-03 — TIMER-PASS-LIMIT-1: the five-minute schedule pass also fits the service’s time limit

It walked the runs in one fixed order, so on a store that needs more than 5 minutes the same runs came last every pass and were never checked. Revision 2026-10-02 — MACHINE-PICK-1: a person chooses which machines a migration moves, before their targets (BUILT 2026-10-02)

§3/§9 — the migrate flow gains a first step. A scan of a resource group, a subscription or a management group finds every machine there, and many are not meant to move (being decommissioned, another team’s, not now). Every machine that could move used to go into the migration, and the only way to leave one out was to take it out of a wave. The migrate flow is now Choose the machines → Choose each target → How to group them → Arrange the waves → Run it.

Choose the machines (new, ruled). The step lists the machines the review lists (never an Excluded or platform-managed one) with subscription, resource group, tags and the assessment group (Can migrate, Some targets only, Cannot yet, Current; READY-NOW-REMOVE-1 removed Already migrated: a machine on NVMe whose size is not Current, such as Ebsv5, can migrate, and GUEST_PREP gives it no SCSI to NVMe preparation). ALREADY-CURRENT-1: a machine whose CURRENT size Microsoft puts in the Current lifecycle stage is in the group Current on every page (the assessment list and report, the wizard, the run page's Machines we found), with the line “<size> is in the Current lifecycle stage.”, never red and never in the Cannot yet count. The scan records the stage (assessment v10 sourceLifecycle, by Get-VmfSizeLifecycleStage from the lifecycle data), so no page reads it from the size name; Set-VmfMachineChoice and the page refuse such a machine by the target options' sourceStage. Nothing is ticked at first. A machine can be chosen only when the target options (target-advice.json) give it a supported series — one rule, held by the page and by the engine. Four filters combine: subscription, resource group (narrowed to the subscription), tag (a name and value, across subscriptions) and name; Add the machines shown and Remove the machines shown act on every machine the filters match, not only the rows on screen. A page of 50 rows with Show more. No reason field, no tag rule, no import and no scan-time filter: those are ruled out. Set-VmfMachineChoice saves machine-choices.json beside the assessment, through the service (POST assessments/{runId}/machines, Vmf.Operator), quoting back the versions the service issued (PLANVER-2) and writing in one step with the check (Write-VmfTextDocumentIfVersion, or a create-only write for the first save).

Downstream. Only a chosen machine may have a target (Set-VmfTargetChoice refuses another with 400), and target-choices.json records the version of the list it was saved against (required since v9). New-VmfPlan plans only the chosen machines: a machine left out gets no plan entry, so no target and no wave, and stays in the assessment and its report. The engine’s plan operation refuses without a list on every request, a request that names one series included (-RequireMachineChoice), refuses targets saved against an earlier list, and refuses a plan that would hold no machine. The run page and the report call a machine the plan has no entry for “Not in this migration”, never ready. The targets step and Export for pricing show the chosen machines only. A machine is added back only through this step, which means saving the targets and planning again; the wave editor gains nothing. The list comes first. The wizard saves the list before any target, so it never reads saved targets as the list: with no list it opens the machines step with nothing ticked, whatever a link asks for (OLD-VERSION-READERS-REMOVE-6). The engine never does either (TARGETS-NO-LIST-1): Set-VmfTargetChoice refuses to save a target with no list (400), and New-VmfPlan refuses targets saved with no list, and a target-choices.json of any version but its own. The Assessment column shows the review’s group; a machine the review clears but the target options give no size cannot be ticked, and its row says so. The target options are still made for every machine: they are what decides which machines can be chosen.

Revision 2026-09-26 — ADVISOR-1: the target is chosen per machine, before the waves (BUILT 2026-09-26)

§3/§9 — the flow gains a step. Microsoft’s order is assess, then plan each machine’s target, then group into waves. The flow becomes Assess → Review → Choose targets → Plan waves → Migrate → Validate. Since GEN-V5-1 (2026-09-26) there are three target series — v5 (the Extended stage; a resize on SCSI, Generation 1 allowed, Microsoft’s “smoothest transition”) and v6 and v7 (Current; the NVMe move, Microsoft’s “latest features and performance”) — and a fleet has machines that can take some and not others.

Choose targets (new). When an assessment review is approved, the engine works out the options for every machine automatically and writes target-advice.json beside the assessment: for each machine, each series (v5, v6 and v7; the product has no Generation 1 to Generation 2 route, GEN1-ROUTE-GONE-1). Each option carries facts only — the target size and whether the region offers it; the blockers that apply to that series; the kind of change (a resize, an NVMe move, a Path B rebuild around the same disks); Microsoft’s lifecycle stage of the size moved from and to (a v4 to v5 move stays Extended and is never shown as an upgrade); and what accelerated networking does on the target size, judged from the primary interface as the engine does (AN-PRIMARY-1). Whether this product’s lab has proven a kind of move is not shown yet. A size that does not support encryption at host, or Ultra Disks in the machine’s zone, when the scan found the machine uses it, is not offered (TARGET-CAPABILITY-PRECHECK-1, reasons no-encryption-at-host and no-ultra-disk, target-advice v33) - also when the catalog does not say. A fact that could not be read is shown as unknown, never guessed.

How a target is set (ruled). One default for the whole migration: a Microsoft lifecycle stage, Extended (v5) or Current (v6), defaulting to Current. Any machine can be changed to v7 where v7 is supported for it. Every machine starts on that default where it is supported for that machine, otherwise on the other supported series, otherwise with no target and its reasons. Accelerated networking first (ADVISE-AN-1, 2026-10-10): a machine that uses accelerated networking today does not start on an option where it certainly stops working when another supported option certainly keeps it — see the accelerated networking callout in §9. No rebuild (REBUILD-REMOVE-PLAN-1, 2026-11-07): every target is the in-place upgrade, or the in-place upgrade (Preview) for a Windows machine whose move changes the kind of temporary disk, so no start rule moves a machine off a rebuild any more (REBUILD-PICKER-1’s and IDENTITY-LOSS-1’s are gone). The targets step names the kind of change of every option (“v6: In-place upgrade (Preview)”), and target-choices.json (v8) and each plan entry’s target.choice.method (v29) record it: in-place or preview. For each subscription where a machine’s target is a Preview and the feature is not registered, the step says so and how to register it in the Azure portal; the product never registers it. The plan refuses a saved method the rules no longer give. A person may change any machine to any other supported option — an unsupported one is shown with its fact and cannot be picked — one machine at a time (the tick boxes are gone, 2026-10-12). target-choices.json records who chose what, against which advice. Planning from the app is refused until targets are saved: the engine’s plan operation, which the dashboard and the API both reach, passes -RequireTargets unless the request names one series. A command-line call without it plans every machine on one series, as before. The save quotes back the document versions the service issued (PLANVER-2).

Plan waves. Each machine is resolved against its own chosen series; the series and size belong to the plan entry (target.choice, plan-entry v15), not to the wave. A chosen series with no size is reported with its reason and never switched. A wave answers when and how — grouping, timing, approval, concurrency, capacity — not what a machine becomes, and may hold several series. The wave’s series control that once moved every machine in it was removed by WAVE-SERIES-GONE-1; source = wave remains readable in plans written before. One machine’s series can change after planning (WAVE-MIX-2, Set-VmfMachineTarget): only to an option the saved target advice calls supported, only when a recompute against the saved catalog agrees with it, never once any machine in its wave has a state document or a lease, never while the wave has a capacity reservation (held or released); it clears the wave’s acceptance, approval and quota check before it writes the plan, asks again after the write, and puts the plan text and those records back if a worker took a machine of the wave meanwhile. A machine that ROLLED BACK may take another series while nothing in its wave is running (RETRY-SERIES-1, Set-VmfMachineTarget -AfterRollback, offered on the run page beside the machine): the same recompute and the same clearing. The machine stays rolled back, and is tried again with Retry once its wave is accepted and approved again; re-arming it at once would leave it at PRECHECK waiting on a sign-off, reading as running and refused by Skip, which is why the retry itself refuses until the wave can start (RETRY-GATE-1, §7). The plan sign-off of the exact plan lapses too; every other wave keeps its own approval, because a wave approval signs its own wave (WAVE-APPROVE-1). Start-VmfWave passes the version of the wave its start checks passed (Get-VmfWaveVersion) to each worker, and a worker whose read gives another version takes no machine; each time a worker leases a machine it compares that entry with the stored plan (Test-VmfLeasedEntryCurrent) and leaves the machine untouched when its wave, path or target changed. When only its policy or its decisions changed - what a person’s decision on a stopped machine of the running wave writes - the worker runs the STORED entry if the wave, as stored now, passes its start gates (Get-VmfWaveStartGate, the gates the decision asked before it put the machine back), and else leaves it untouched; it compared no decisions before, so a rebuild accepted for one machine was run on the worker’s old copy and stopped again at Checking (REBUILD-ACCEPT-MACHINE-1, measured 2026-11-04). Once a machine is past PRECHECK it finishes the move it started: PRECHECK records captured.startedTarget (path, the whole target, series and accelerated networking) and a resume whose entry differs uses the record, with a warning in the activity log - never a park mid-move, which would leave the machine stopped or half rebuilt (STATE-TARGET-1). A decision may not change the size series: a machine that has started keeps it, and another series means planning the machine again. The run page’s acceptance summary counts the series across a wave’s machines. Supersedes WAVE-2 lever 8 (“the target generation is a per-wave lever”) and GEN-ONCE-1 (the series choice moved out of the plan wizard).

Revision 2026-08-28 (evening) — WAVE-2 shipped, three safety holes closed, and the flow met its first real user

§7/§9: WAVE-2 is built. The ring taxonomy is gone from the contract, the engine, the facade and every screen — waves carry names the customer types, and the planner generates only neutral starting names. Every wave’s options must be reviewed and ACCEPTED by a person before it can run, bound by hash to that wave’s exact membership and levers, refused engine-side so no interface can skirt it. All eight levers were ruled one at a time; approval now defaults ON and the gate FAILS SAFE (an entry silent about approval is treated as requiring it). Snapshot retention is enforced rather than decorative (Remove-VmfExpiredSafetyCopies, and a restore now says who deleted the copies and why). The target generation is a per-wave choice, v6 by default, and a v7 wave in a region without v7 is refused with the v6 size named rather than silently substituted. (Superseded 2026-09-26 by the ADVISOR-1 direction above: the series will be chosen per machine, before the waves. Until ADVISOR-1 and WAVE-MIX-1 are built, the per-wave choice is what ships.)

§8/§12: LINUX-TEMP-1, found by a live failure and closed with measurement. A v4→v6 Linux machine failed validation on its temp-disk fstab entry. Measured on real hardware: a machine BORN on v6 does not mount /mnt either and has no such entry — so that is normal Azure behaviour and the dangling entry is a migration artifact. Microsoft states the customer must format and mount the raw NVMe drive on every start; no agent does it. Built the Linux twin of the Windows temp-disk boot task, and taught validation to treat a nofail entry as a fact rather than a fault. Proven end to end: the drive returns after a restart, and the guest validation that failed now passes.

§7/§11 — a real safety hole: leases were scoped to the RUN, so two runs over one resource group could lease, deallocate and convert the SAME machine simultaneously, each believing it held it exclusively, inside the deallocated window. Machine claims now live beside the runs and gate at lease time; a claim whose run no longer exists is reclaimed automatically, and an operator can take one back deliberately. A run also gains a visible life — setup, planned, running, finished — can be STOPPED when nothing can finish it, and can be deleted, with the before-migration copies an explicit choice and the deletion recorded outside the run it removes.

§10/§13 — the finding that matters most: the setup flow was driven end to end for the first time, and that found a great deal. Every defect shared one shape: the system knew something the person could not see. The engine refused a wave and wrote the reason to a container log and nowhere else; a wave rename orphaned its capacity check silently; a button was wired but said nothing when it had nothing to do; the wizard skipped a gate the engine enforces; a redraw discarded what he had just typed. All are fixed, and the engine now records a refusal INTO THE RUN STORE where every surface can show it. The lasting change is mechanical guards for the whole class: a test that fails when a control is rendered that nothing binds, a function nobody calls, a nav that differs between pages, the same lever named two ways on two pages, an endpoint calling a function the module manifest does not export, or a page loading a file the deploy does not ship.

03Product vision & principles

A migration factory, not a bigger script: the customer feeds it a scope, and it produces assessed, planned, migrated, validated VMs — with evidence.

The product mirrors the four Microsoft phases as four explicit commands a customer runs in order, each producing an artifact the next consumes:

1 · AssessDiscover fleet via Resource Graph, run readiness rules, classify every VM: Ready / Needs-prep / Blocked / Out-of-scope. A size list that cannot be read for one subscription and region, after the retry of every Azure call, does not stop the scan (SCAN-PARTIAL-SUBS-1, assessment v14): it is recorded in notRead with Azure’s reason and the role the permission map names, its machines are held (sizes-not-read), and the other subscriptions finish. Each machine records encryptionAtHost and ultraSsdEnabled (TARGET-CAPABILITY-PRECHECK-1, assessment v17), so a target size that does not support them is not offered. Output: assessment.json + HTML report.
2 · PlanChoose each machine’s target (ADVISOR-1), then select the migration path, group into customer-named waves by dependency, pre-check quota & capacity per wave. Approving the review starts the engine’s advise operation, which writes target-advice.json beside the assessment: for each machine, v5, v6 and v7 with facts only — supported or not and why, size, path, kind of change, lifecycle stage from and to, accelerated networking — and the option it starts on under the migration’s default, Current (v6) or Extended (v5), Microsoft’s lifecycle stages. A person changes any machine to another supported option, v7 included. The wizard’s first migrate step, “Choose the machines” (MACHINE-PICK-1), saves which machines move; the second, “Choose each target”, saves their targets. Only chosen machines are planned. Output: target-advice.json, machine-choices.json, target-choices.json, plan.json.
3 · MigrateExecute one wave, or a whole signed-off plan wave after wave (PLANRUN-1): parallel per-VM state machines with checkpoints, retries, circuit breaker, automated rollback. Output: per-VM state documents + the run’s activity log.
4 · ValidatePlatform validation on every migrated VM inside the migration itself, then the Reports page and the migration record (ATTEST-1) as evidence. Output: reports and the record.

Principles

  • Everything is resumable. Every step is idempotent and checkpointed to durable state. Re-running a wave skips completed VMs and resumes half-done ones from their last good step. A crash never requires archaeology.
  • Plan is a reviewable artifact, not a side effect. The customer (and their change board) approves plan.json before anything mutates — per wave, or once for the whole plan (PLANRUN-1), which writes one approval per wave — and each approval is bound to the version of its own wave (WAVE-APPROVE-1: Get-VmfWaveVersion, every entry of the wave and the plan-wide fields), signed only when the plan version the service issued is the one the approver was shown (PLANVER-2). A change to one wave asks again for that wave only. Every write of the plan checks that version and writes in one step (Write-VmfTextDocumentIfVersion: If-Match on blob storage, a lock file on the file backend), so two writers at once give one 409, never a lost change (PLAN-WRITE-RACE-1). A plan with a machine where the scan found SQL Server (plan-entry v37 assessment.sqlServerDetected), moving from a SCSI temporary disk to an NVMe temporary disk or none, is signed off only when the approver names each such machine as checked for where tempdb is (SQL-TEMPDB-SIGNOFF-1, 2026-11-16: Test-VmfSqlTempdbRisk, plan-approval v4 sqlTempdbChecked); a wave approved on its own is refused for such a machine the sign-off does not name.   • Safety is not optional. Two locked safety copies on every machine; any failure puts the machine back; an approval before a wave runs; circuit breaker inside waves. (The bootable-clone tier of the original plan is not built; a plan that asks for it stops, §11.)
  • The guest-prep logic is a shared library. The proven check/fix scripts from both existing files become versioned, individually testable script assets consumed by every path.
  • Lab-first. Every feature ships with a lab scenario that exercises it, including its failure mode.

The guest-script contract

Every guest asset follows one contract, which is the biggest single engineering change from today's scripts:

06Interface strategy: beyond PowerShell

PowerShell is not the architecture — it's a client. Every mutation the product performs is an ARM REST call (RunCommand included). The question is not whether we can move off PowerShell, but when each layer should.

One clarification first: "native ARM" here means calling the ARM REST APIs directly — not ARM templates/Bicep. Declarative deployment languages cannot express this workload: it's a stateful, imperative sequence (prep the guest, verify, deallocate, mutate, start, validate, maybe roll back) with decisions between steps. That's an engine's job, whatever language the engine is written in.

Where PowerShell actually sits

Five layers. Two are swappable — and PowerShell happens to occupy both of them today. Three are permanent — and none of them is PowerShell-dependent. "Moving off PowerShell" only ever means swapping the top two layers; Azure sees identical ARM calls either way.

Every store request reuses a connection (PAGE-LOAD-FREEZE-1, 2026-11-07). Each store request of the service went through Invoke-WebRequest, which opens a new TCP connection for each call, and the schedule timer alone makes about 700 store calls a pass. On the Consumption plan an instance has 128 SNAT ports for one address and port and gets a closed port back only after four minutes (Microsoft, Troubleshoot intermittent outbound connection errors in Azure App Service), and on the lab install store calls stalled for 65 to 110 seconds and ended together - with a page open and with none. Every store request now goes over one HttpClient for the whole process (Send-VmfStorageHttpRequest, Get-VmfStorageHttpClient), shared by the reads sent together, with a connection life of 5 minutes so a changed storage address is seen. It sends with HttpClient.Send on the calling thread, and each read sent together on a thread of its own (STORE-CALL-SLOW-1): a request that waited on SendAsync needed a second thread-pool thread, the service's runspaces held them, and on the lab install each store call then waited about 450 ms. Over TLS a reused connection still needs a thread-pool thread for one read, with Send as well, so the process raises the pool's minimum to 64 when it makes the client (Set-VmfStorageThreadFloor): below its minimum the pool adds a thread at once. What held the pool's threads on the lab install was Azure PowerShell's own data collection (FACADE-PASS-SHARE-1, 2026-11-10): each store request asked Get-AzAccessToken for its token (the engine still does; the web service has used the managed identity endpoint since FACADE-SIGNIN-COLD-1), and each Az cmdlet call sends usage data to Microsoft from a thread-pool thread that waits for the send. With those sends waiting, a schedule pass held about 270 pool threads and its store calls waited in steps of about 500 ms; measured on this computer against the real module, 302 busy threads and a median of 1006 ms a call, and with the data collection off, 6 and 1.1 ms. So the engine's start-up script turns it off at Process scope before its first Az call, and any process turns it off when it makes the client (Set-VmfAzDataCollectionOff); it reads the setting back, and names the result in its VMF-POOL and VMF-CALLS lines (azData). Nothing is written to disk, and the engine's processes get it too.

A store request has a time limit (STORE-REQUEST-TIMEOUT-1, 2026-11-09). Each attempt of a store request waited the HttpClient default of 100 seconds, and a request made up to five attempts, so a store that never answered held a call for about eight minutes - past the five-minute limit of the service on Consumption. On the lab install a schedule pass ended at that limit after one store request waited about 3.5 minutes. In the service an attempt now waits at most 20 seconds with no answer - for the headers of the store’s answer - and the whole request at most 40 seconds with no answer, its waits between attempts included (Get-VmfStoreRequestLimit); a request that gets no answer has two attempts, and one that fails at once still has five. The body is not held to those limits (2026-11-09): once the headers come, the body has the 100 seconds the service had before, and a body that fails is sent again as before. The client drains nothing from an answer it stops reading, so a body read ends at its limit. The slowest store answer measured on the lab install since the pooled client is 2.7 seconds. The schedule and cleanup passes stop starting runs at 210 seconds, and two requests with no answer still end inside the limit. Each read sent together is the first attempt of its request, and a read sent again keeps the time it waited for headers. The engine has no five-minute limit, and a failed checkpoint can stop a move, so its attempts stay at 100 seconds each, five in all. The service is known by FUNCTIONS_WORKER_RUNTIME, the setting Azure Functions requires of every function app. A version-checked write whose answer was lost and that was sent again meets its own text, which Write-VmfTextDocumentIfVersion already reads back as a success (PLAN-WRITE-RACE-1).

The unified failure model — BUILT and DRILLED 2026-08-28 (15/0 on real hardware)

Directed, and it reframes the three failure states above into one outcome with one remedy: any failure returns the machine to the pristine copy and its original size and controller, then records it as needing attention. (Two ends Azure can refuse - no capacity to start the machine on its original size, or a refusal of that size - are below: ROLLBACK-CAPACITY-1.) (No exception: when Microsoft retires the original size, a machine on it is outside the scope of this tool from one day before the date and is refused at PRECHECK, untouched - RETIRE-SCOPE-1 in §18, which removed the nearest-current-size rollback V3-RETIRE-1 had added.) Not a policy, not a per-wave lever — the behaviour of the product. As built: evidence (boot diagnostics) is captured BEFORE the rollback and failing to capture it never blocks the rollback; a specific classified cause (capacity, lock, permissions) wins over the generic "rolled back" so the actionable part survives; every stop records machineState (untouched / restored / changed — only a stop whose rollback did not finish may claim changed - since PREP-ROLLBACK-1 that includes one whose own stop failed before any disk changed, which keeps its cause as the reason); and the drill proved the disk that comes back is genuinely the pristine one, from ARM's own lineage record, not inference. The old bootFailure/validationFailure levers are gone from the contract, and a stale plan still carrying them cannot resurrect the hold.

The reasoning is a product position, not a technical default. Migrations run in a change window, so there are no writes to preserve — the same logic under which nobody plans to roll back a patch and keep the writes. And the support argument is decisive: a tool that sometimes leaves a machine in an in-between state needs someone to call when it does. A customer who does not want that is not a customer for this tool. One sentence a customer can hold us to beats a matrix of conditional behaviours.

Consequences, deliberately accepted: the pristine copy becomes load-bearing — which is why it is mandatory on every wave and why a run refuses to start when the copy cannot be taken. The policy levers bootFailure and validationFailure disappear; there is nothing left for them to choose. (Corrected 2026-09-26: this sentence used to say onDDataFound and onDriverBelowFloor disappeared too. They survive, in plan-entry v14, because they are not failure handling: they ask, before anything starts, whether the customer accepts a known risk (since AN-PROCEED-NETVSC-1, 2026-11-06, onDriverBelowFloor accepts none: its values are stop and, per machine, updateKernel) — see docs/schema-migrations.md, FAIL-1.) Forensics survive, because boot diagnostics are captured before any rollback — the one real argument for ever leaving a machine broken. And the single case that cannot honour the rule keeps its own treatment: when the rollback itself fails, the machine is not as it was, and it says so rather than offering a retry that cannot work.

When Azure has no capacity for the original size, or refuses it (ROLLBACK-CAPACITY-1, 2026-11-14). Microsoft restricts capacity growth for older series (target-families.json lifecycle.capacityRestrictions, from the pinned page retirements-and-capacity-restrictions), and a rollback returns a machine to its original size, so the model above has two ends it cannot promise. (1) The start at the end of the rollback is tried again on an allocation failure (AllocationFailed, ZonalAllocationFailed, OverconstrainedAllocationRequest, OverconstrainedZonalAllocationRequest, from Microsoft's page on allocation failures): 4 tries, 120 seconds apart, with the lease renewed around each wait (Start-VmfRollbackVm). Still no capacity: the stop is FAILED_ROLLED_BACK with the reason rollbackNoCapacity - every disk is back from the pristine copy and the machine is stopped on its original size; only its power state differs from before the move. (2) Azure refuses the original size itself (SkuNotAvailable, NotAvailableForSubscription, or OperationNotAllowed that names a quota or the size - Get-VmfSizeRefusalCode): the rollback stops before any disk swap, FAILED_NEEDS_ATTENTION with the reason rollbackSizeRefused, the machine stopped on its new size, and the stop lists each setting the rollback already put back (accelerated networking, the capacity reservation group, disk types). Any other failure of the size change stays rollbackFailed. The product gives no guarantee of capacity, so the plan records it per machine: plan-entry v35 assessment.sourceCapacityRestricted (true, false, or null when not known), and the sign-off of a wave with such a machine says so in one line.

When the rollback cannot end on the original size (ROLLBACK-NO-CAPACITY-OTHER-SERIES-1 and ROLLBACK-SIZE-REFUSED-SERIES-1, 2026-11-14: the machine moves to another series, for example v5, as a fresh run from the original disks with new safety copies, and v5 stays on SCSI). Two stops of ROLLBACK-CAPACITY-1 have that way forward. rollbackNoCapacity (every disk back, the machine stopped on its original size): a retry of a move onto v5 or Bsv2 starts the machine on the new size (captured.startOnTarget, vm-state v51). Checking runs every check that reads Azure and does not start the machine; the new attempt takes new copies (-a2) of the original disks and keeps the readings the earlier attempt took of them; Preparing runs no script; Converting resizes the stopped machine; Starting starts it on v5 and then runs the checks that read the guest (the LVM devices file, the cluster check, the SR-IOV unmanaged check on a Linux move with accelerated networking on after it - VF-UNMANAGED-CONFIG-1, sriov-unmanaged-check.sh - and the driver check), and a check that stops is a full rollback. Only a move that needs no change inside the machine before it qualifies: not NVMe, and not a Windows machine whose page file must move or that needs the MANA driver in its store. rollbackSizeRefused (the machine stopped on the new size, on the disks the move left): Change to v5 is offered for that stop too, a SCSI series only until a restore, and Restore this machine from the first copy then puts the disks of the first safety copy onto the v5 size of the plan. This is the one place where "restored" is not "on its original size": the restore records it (restore.ontoTarget), and the size becomes the first capture's (captured.original.sizeReplaced keeps the size Azure refused), so every later rollback and restore returns the machine to the v5 size. A machine in its own capacity reservation group, or a Preview move, is refused that restore before anything changes.

Before the move too (PREP-ROLLBACK-1, 2026-10-05): the machine is rolled back. As first built, the rule ran from CONVERTING on: a guest preparation script that failed after it rewrote the boot path left the machine half prepared as FAILED_NEEDS_ATTENTION, and a shutdown or second copy that failed after the preparation started the prepared machine again — the shutdown's stop even said nothing was changed. Now a stop in GUEST_PREP, STOPPED or SAFETY_COPY after a script in the same attempt changed the guest, or may have, rolls the machine back from the pristine copy — FAILED_ROLLED_BACK, with the cause kept as the reason code. The audit trail decides (Get-VmfGuestChangeThisAttempt): a script that changes the guest gets its audit entry before its run command, as STARTED, and the same entry takes its result after — so a script that changed the registry and then timed out, or a worker that died while it ran, still counts. A MANA install that added files says so itself. The hardware, disk types, reservation and accelerated networking have not changed before CONVERTING, so this rollback swaps the disks only (Invoke-VmfRollback -GuestOnly): stop, every disk from the first copy, start — never deleting a machine's definition, and on the disk types and size the machine has now. A stop that changed nothing still leaves the machine as it was, with no rollback. Every automatic rollback is checkpointed (rollbackPending, vm-state v19): written before its first change, removed in the same write as the stop that ends it; a worker that finds it finishes the rollback before any step runs, so the step that failed never runs again on a half rolled-back machine. Each disk a rollback makes is recorded the moment Azure makes it (rollbackDisksDuringRollback), and the disks the machine runs on are recorded after each swap. A disks-only rollback that fails is never followed by a start while a data-disk LUN may be empty (SWAP-2UPD-1); one whose own stop failed before any disk changed keeps the cause as the reason, with the machine changed, for a person to restore from the first copy.

Why a stop must say what to do about it

Every stop carries a reason code (history[].reasonCode), resolved against data/stop-reasons.json (26 codes as of 2026-09-26), which states per code: what stopped it, what it means, what to do, where it left the machine (untouched / restored / changed), and whether retrying actually helps. This exists because the question "realistically, what could a customer fix before hitting retry?" has a counter-intuitive answer worth designing around: most stops happen before the machine is touched — permissions, capacity, a target size holding fewer interfaces or data disks than the machine has, a kernel below the driver floor, data on the temporary drive, a hibernated machine, a resource lock. Most of the codes are of this kind. Those retries are free and the fixes are real. Where a stop is really a choice — data on the temporary drive, a kernel below the MANA floor, a system-assigned identity — an approver can decide for that one machine and continue (DECIDE-1, DECIDE-2, Resolve-VmfDecision; the approver role alone is enough; without the operator role the engine accepts only the decision the machine waits for — the setting of the park it waits at now (the last history entry, with nothing rebuilt or restored since), alone, at exactly its accepting value, compared character for character — because everything else the call does is a retry, which is the operator’s (DECIDE-ROLE-1). A setting changed this way, or by a wave save, takes one plain value and one name, both compared character for character (ordinal)), or leave that one machine out of the wave (SKIP-ONE-1, Skip-VmfVm). A retry or a decision is refused while the machine’s wave would fail the engine’s start gates (Get-VmfWaveStartGate: acknowledged, accepted, approved or set not to need it — the same list the restart timer asks before it starts a stalled wave): the refusal names the missing step in the gate’s own words (GATE-WORDS-1: each gate returns a stable code, the gate it belongs to, and two sentences from data/start-gates.json — what is missing and which button on the migration’s page does it — and every caller asks the code, never the words; a refusal for changed settings is logged once, as the wave start and both timers log it, so the page offers the acceptance again), the run page shows it in the dialog where the person pressed Try again, and nothing is re-armed. A decision that changes a setting carries the wave’s accepted settings past its write (DECIDE-KEEP-1). The wave’s own approval is carried only when an approver accepts the one decision the machine waits for: the approval keeps the name of the approver who gave it and gains an amendment naming the approver who decided (WAVE-APPROVE-1). A plan sign-off of version 3 moves only together with that approval, because a sign-off of the exact plan passes every wave at the gate: moved past an operator’s decision, it passed the decided wave with its approval removed (the rule since 2026-10-10). The post-conversion failures are the short list, and their guidance says so rather than implying a retry will work.

Two rules hold the honesty in place. Unknown stays unknown: a code with no guidance renders the raw engine detail rather than an invented explanation, and an unrecognised ARM error stays a general failure rather than being classified into a wrong cause that sends someone to fix the wrong thing. Design note — the prompts problem

Every AskToContinue in the current scripts maps to one of three things in the state machine: a plan-time choice the customer makes per wave, a stop that waits for a person (resolved by fixing the named cause and trying the machine again), or a hard stop that was never really a question (safety-copy failure). This is what makes unattended parallel execution possible without losing the safety the prompts provided.

Vocabulary note (raised 2026-08-27): "park" was engine jargon that never had a customer-facing definition, and the choice offered on a stopped machine — "run the safety checks again" versus "only repeat the final health checks" — was engine vocabulary dressed up as a question. The engine derives that answer itself now; the operator gets one action, try this machine again, and a plain statement of what to fix first.

Execution model — how a script runs in parallel safely

The safety does not come from the PowerShell parallelism primitive; it comes from the coordination design around it. The primitive is deliberately boring: an orchestrator process that spawns N worker pwsh processes (the wave’s “machines at once” setting, 5, 15, 30 or 60, default 15, up to 15 per container), each running one per-VM state machine at a time. Above 15 the service splits the wave across up to four Container Apps job executions, 60 machines at once in all, sharing one run store (SCALE-2); a container that finds nothing to lease waits while others still hold machines, and a container that dies is not replaced — the survivors reap its leases and finish the wave. The container is sized from its worker count, measured at about 540 MB per working worker (SCALE-DRILL-1): 1–3 workers on 1 CPU / 2 GiB, 4–7 on 2 / 4, 8–15 on 4 / 8. Process isolation is chosen over ForEach-Object -Parallel runspaces as the default because the Az modules have known thread-safety and memory-growth issues under high runspace concurrency, and because a crashed worker then costs one VM-step, not the run. Thread workers remain a later optimization behind the same interface.

2 · Heartbeats + watchdogWorkers renew their lease at every state boundary and inside long steps: every ARM call passes through one wrapper, which renews the lease (throttled) before each operation — as-built refinement from a live Stage 3 finding, where a state running several 60-second guest commands outlived the timeout and a healthy worker was falsely reaped. The orchestrator's monitor loop reclaims leases whose heartbeat expired and marks the VM resume-needed. A reclaimed lease is fencing, never a step failure: the displaced worker abandons cleanly — no failure transition, no rollback — and the new holder resumes from the checkpoint. Every change to a lease after its create is one step with its check (LEASE-HEARTBEAT-RACE-1, the plan’s own mechanism, PLANVER-2): a renewal writes only if the lease is still the text it read (If-Match on Azure, the lock file locally), a removal removes only the text it read and waits for that lock, and the watchdog removes a lease only as it judged it expired. Infrastructure-as-code fleets

Many fleets are managed by Terraform, Bicep, Pulumi, ARM or Ansible, and a converted VM whose config still says the old size is a time bomb: the customer's next apply reverts the migration — or, where a changed attribute forces replacement, destroys and recreates the VM. The product's posture is unchanged and absolute: never touch customer state or config. Module structures and pipelines vary and the blast radius is unbounded.

WAVE-2 — rings are our vocabulary, and they were removed (directed 2026-08-27; BUILT 2026-08-28, plan-entry v5)

The reason: lab, canary, prod and non-prod were invented here, and not every customer uses those terms. Every decision is the customer's during migration planning: each wave takes any name the customer gives it, not a fixed set of ours, and each setting is a lever to pull per wave.

This came out of auditing the ring policy table, which was completely invented and fully problematic. Four of its eight settings were defects: a safety copy silently weakened below production, a retention setting nothing reads, the IaC gate above with no surface to operate it, and a capacity gate duplicated where the wave editor overwrites it anyway. But the deeper problem is the taxonomy itself: ring is a closed enum in the plan contract, wave names are generated from it, and it carries every policy default — so choosing a name silently chooses eight behaviours.

The model: a wave has a name the customer types; every policy is an explicit lever on that wave, set during planning; and no fixed environment vocabulary exists anywhere in the contract or the UI. Every wave must force a deliberate selection — defaults may be offered, but they must be clicked and accepted, never inherited from a name. The safe end is the default and every loosening is a deliberate act, consistent with the pristine-copy ruling. As built, each lever was ruled one at a time on 2026-08-28. 10Capacity assurance: quota & ODCR workflow

Across 7+ regions, compute availability is a program-level pipeline that runs ahead of the waves — because quota tickets take days and On-Demand Capacity Reservations bill from the moment they exist. Waves never gamble on allocation.

The demand matrix

The planner derives a demand matrix from plan.json: for every (region × zone × target family × size), the instance count and vCPU total each wave needs — plus the peak shape, which differs by path:

  • Paths A/B (convert in place): the source VM frees its old-family capacity only as the target allocates. Peak target-family demand = the wave's concurrent-conversion count (bounded by the throttle), but reservations are sized for the full wave so a converted VM is never competing for capacity on restart. (There is no redeploy-alongside path, so the source and target never run at once; the claim field that described that overlap is always false, PATH-C-1.)
  • Old-family quota is not the constraint — new-family quota is. v6/v7 families sit in their own quota buckets; a subscription full of Esv5 quota has zero Eadsv7 headroom until requested.
  • Demand is totalled per quota family first (ODCR-FAMILY-1): two sizes that bill to one family are judged together against that family’s headroom, never each on its own, and the family comes from the SKU catalog, never from the size name.
  • The Total Regional vCPUs quota is judged too (REGIONAL-VCPU-QUOTA-1): Azure refuses on it as on a family, and it is read from the same usage list (cores), so no Azure call is added. A machine asks it for the vCPUs it ADDS - its new size less its old one, never below 0, because Azure counts the old size, deallocated or not, until the move gives it back. One machine’s smaller size is never set against another’s larger one, because the order they run in is not known. A machine a capacity reservation holds in a Reserved wave asks for its whole new size: the reservation needs quota as a VM create does, and is made while the old machine still counts. Only a record whose machines add vCPUs is blocked, with regional-quota-shortfall; a family that is short keeps quota-shortfall, and the record says beside it whether the region is short for its machines too (regionalShort, capacity-claim v14, REGIONAL-QUOTA-BOTH-1). One rule says a record is short of the region, for the request and for the migration page’s capacity card alike: Test-VmfClaimRegionalShort, twinned in help.js and held to tests/fixtures/regional-short.json (REGIONAL-QUOTA-BOTH-PAGE-1). Each record also carries what its own machines add (demand.regionalAdds), which gives the regional row of the request confirmation a line for each wave (REGIONAL-QUOTA-WAVES-1). Request-VmfQuota asks for the regional quota too (REGIONAL-QUOTA-REQUEST-1): one Microsoft.Quota request per subscription and region, with the resource name cores (probed 2026-11-02), to quota.regionalUsed + demand.regionalVcpus, never below the present limit. A record short on both is in both requests, filed in one press; its family request moves it to QUOTA_REQUESTED, and the regional one is recorded beside it in quota.regionalRequestId. Azure approves a request at once (HTTP 200) or takes it for later (HTTP 202); for a 202 the engine then reads each request filed in the last 2 minutes, from the stored records, through Microsoft’s Quota Request Status GET (Get-VmfQuotaRequestState, Microsoft.Quota/quotaRequests/read, optional in the execute role) every 15 seconds until Azure answers or 2 minutes after the request was filed, and writes one quotaAnswer line for each with the request ID: APPROVED (Succeeded), REFUSED (Failed or Invalid, with Azure’s code), WAITING (no answer in the time) or NOTREAD. The wave editor shows each answer and the next step: Check the quota again, a support request in the Azure portal, or the Quotas page of the portal (QUOTA-REQUEST-POLL-1, measured 2026-11-16: InProgress, then Failed with QuotaNotAvailableForResource about 80 seconds after the request).

Fallback ladder on BLOCKED NOT BUILT

The claim schema has a fallback[] field for these four actions, but no code writes it: today a blocked claim is shown with its reason and a person acts on it. The ladder stays the design:

  1. Alternate zone — if the workload's zone pinning allows (recorded per-VM in the plan). A zone move is itself a recreate, and no move recreates a machine since REBUILD-REMOVE-1, so it is not offered.
  2. Alternate size — the plan carries the ranked alternates the planner gave each target (e.g. E8ds_v5 → E8s_v5); the claim retries down the list and the substitution is stamped into the plan for the affected VMs.
  3. Split or slide the wave — reserve what's available, defer the remainder to a re-forecast claim.
  4. Escalate — emit a capacity-request package (region, zone, size, quantity, window) for the Microsoft account team; claim parks until resolved.

Every rung is a recorded plan mutation with an owner — never a silent runtime substitution.

Cost guardrails

  • ODCRs bill at the VM rate from creation, used or not. Hence create-late / release-promptly as the default lifecycle, with the reservation window (target: < 72 h per wave) shown in the wave report alongside its cost.
  • Reservations + discounts stack. If the customer buys Reserved Instances / savings plans for the target families (§2 commercial gap), those discounts apply to matching reserved-but-unused capacity too — the commercial replan and the ODCR window should be decided together.
  • Utilization telemetry: claim documents track reserved vs consumed per size and an estimated hourly cost at retail list price (ODCR-UX-1); the run report shows each reservation’s window, and one still open as “Not released yet, and billed until it is”. The table is “Capacity and cost”, each state in words, and a claim with no reservation shows no reserved count (TERMS-AUDIT-1).

Guests report facts; the engine judges them against the plan

A rule learned twice, from two different drills, and it governs this whole section. A guest script must never hard-assert a direction-specific expectation — "the boot bus must be NVMe" is wrong, because a deliberate reversion to SCSI is as valid an outcome as a migration. Bus and driver states are reported as facts; VALIDATING compares them to what the plan asked for.

The same rule caught a subtler bug: a machine's accelerated NIC before migration is Mellanox, not MANA — MANA appears only once it is on its new size. So a driver-readiness question judged against the fabric the guest currently reports answers "Mellanox has no floor" and cheerfully migrates a below-floor kernel into a validation failure. The judgement must be made against the plan's target. And where no floor is published — MANA on Windows, Mellanox anywhere — the answer is unknown, which is never rendered as a pass or a fail.

When none is there, it downloads the ONE pinned package from Microsoft (its URL, version and sha256 are constants in the script, so the guest manifest’s hash covers them, and manifest.json lists them as a package), refuses it on any sha256 difference, refuses it again unless every catalog in it is signed by Microsoft and lists every .sys and .inf file (MANA-SIG-1: Get-AuthenticodeSignature must say Valid AND the signer’s chain must build to a Microsoft root certificate pinned by thumbprint, because Valid trusts any root the machine trusts and a subject name proves nothing; the catalog is read with the Windows catalog API, because an INF has no signature of its own; the package is unpacked in a folder only SYSTEM and Administrators can use, and pnputil runs only when it still holds exactly the files the check read; nothing is installed on a refusal), stages its MANA INF files with pnputil /add-driver, and reads the store again — every add must succeed and the read-back must find the driver. Download-and-verify, not a copy in the repository: Microsoft grants no redistribution right that the product can show, and a RunCommand script cannot carry a 3.9 MB package. Closed schemas, and why the closing had to be enforced

These schemas set additionalProperties: false, and for a while that was decorative: the only contract test asserted that required fields were present, never that unknown ones were rejected. The engine had meanwhile started writing two shapes the contract had never heard of — so the document recording the safety net was itself invalid against the contract. The fix that holds is structural rather than another assertion: every field the engine writes is derived from source and compared against what the schema declares, and disagreement in either direction fails the build. The same shape of guard now covers guest facts, shipped samples, and stop reason codes, because the same class of drift produced a defect in each.

Test tiers

  1. Unit (Pester, no Azure): path selector, size mapper, disk-arch categorizer, state transitions, policy resolution, plan/quota math — the pure logic, and every gate (§17), run in CI on every pull request.
  2. Page tests: each dashboard page’s own functions lifted out and run with real-shaped data, and every page booted in demo mode with no install and no network (TESTPLAN-3).
  3. Guest-script tests: ShellCheck and the Linux guest scripts run in CI’s Linux job, including the temp-disk boot task against fake disks (LINUX-TEMP-3); the guest output is validated against its schema.
  4. Integration (lab, only with an explicit go-ahead): the drills and the dial-driven estate above; every VM must land in an expected terminal state (including the expected-failure profiles).
  5. Failure injection: kill mid-wave and resume (a kill test drilled scale-out, SCALE-2); a failed validation that must come back on the pristine disk (FAIL-1, drilled on real hardware); a failed put-back (GEN1-DISTROS-1).
  6. Scale rehearsal: worker memory and container sizes were measured (SCALE-DRILL-1) and scale-out drilled on five machines across containers (SCALE-2). UNVERIFIED No run of 50–100 machines through one wave is recorded.

Acceptance criteria for "customer-ready"

  • Full matrix passes with zero manual intervention and zero interactive prompts.
  • Any single-process kill at any point resumes to a correct terminal state.
  • Every failure profile produces: correct terminal state + evidence artifact + a machine put back as it was, or, where the rollback itself failed, a machine that says so (the generated runbook of the original plan is not built, §11).
  • Scale rehearsal: ≥ 95% first-pass success on healthy VMs, breaker never falsely trips, HTML report accurate against state files.

17Agent-driven build-out to Stage 3

Fable agents write essentially all of the code. What makes that safe when no person reviews every line: the testing framework is the trust mechanism, the lab is the final judge, and every gate is something a human can verify by running a command and seeing green — not by reading source.

The operating model

Your role shifts from builder to product owner + operator. Agents do specification-to-code; you make decisions, run gates, and hold the credentials. Every unit of work moves through the same loop:

1 · SpecYou + an agent turn one roadmap item into a written spec in the repo: behavior, JSON contracts touched, failure modes, acceptance tests named up front.
2 · Tests firstAn agent writes the tests against the spec — before implementation. You approve the tests (readable English-ish assertions), not the code.
3 · ImplementAn agent (or several in parallel for independent items) writes the code until the tests pass, in a branch, one work item per PR.
▼
4 · Adversarial reviewA separate agent session reviews the PR with a hostile brief: find bugs, find tests that would pass with broken code, check the contract schemas. Findings loop back to step 3.
5 · Lab proofFor anything touching Azure behavior: the relevant lab scenario runs and must land in its expected terminal state. Agents trigger and triage it; you see the pass/fail report.
6 · Human gateYou merge. Your evidence: green CI, green lab, the reviewer agent's report, and a plain-English change summary — never raw diffs unless you want them.
Why this works without you reading code

Three independent nets have to fail simultaneously for a defect to reach you: the test suite (written from the spec, not from the implementation), the adversarial reviewer (a different agent context with an incentive to break things), and the lab (real Azure, real VMs, expected-state assertions — immune to "the mock agreed with the code"). The lab is the one that can't be fooled, which is why nothing that mutates Azure merges without it.

The one discipline that keeps this honest

Never let implementation outrun the lab. The failure mode of agent-built systems isn't bad code — agents fix code fast — it's plausible-looking green: tests that mirror the implementation instead of the spec. The countermeasures are structural: tests written before code from the spec, a hostile second-agent review of every PR, and a lab that asserts on real Azure outcomes. Budget lab spend as a first-class cost (small SKUs, a teardown that reads its own removal back, a set monthly budget on the lab subscription, every run with an explicit go-ahead) — it is the cheapest insurance in this entire program.
